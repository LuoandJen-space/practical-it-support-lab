# Windows Event Viewer

## 1. Purpose

Windows Event Viewer provides access to event logs recorded by Windows components and applications.
Event Viewer provides evidence about recorded events. An event does not necessarily identify the root cause of an incident.

## 2. Event Log Categories
### System

The System log records events generated by Windows system components, including the Service Control Manager and other operating system components.
It can help investigate:
- Service failures
- Driver-related events
- System startup and shutdown
- Unexpected restarts
- Operating system errors

### Application

The Application log records events generated by applications and application-related components.
It can help investigate:
- Application crashes
- Application errors
- Application warnings
- Problems reported by installed software

### Security

The Security log contains security-related audit events, depending on the system's audit policy and permissions.
It may be useful when investigating account activity, authentication, or other security-related issues.
Access to some logs and event details may require appropriate permissions.

## 3. Understanding Event Fields

Log Name: The log in which the event was recorded
Source / Provider: The component that generated the event
Event ID: An identifier for the type of event reported by that provider
Level: The event's assigned severity or classification
Date and Time: When the event was recorded
User: The account associated with the event, when applicable
Computer: The computer associated with the event
General / Message: A description of the recorded event
Details : Additional event data, when available

### Event Levels

Common levels include:
- Critical
- Error
- Warning
- Information
- Verbose, where supported
An Error or Warning does not automatically mean the computer is faulty. The event's meaning depends on its provider, message, context, and relationship to the reported symptom.

## 4. How to Inspect Events

### Step 1 Open Event Viewer

1. Win + R
2. Enter eventvwr.msc.
3. Expand 'Windows Logs'.
4. Select 'System' or 'Application', depending on the issue.

### Step 2 — Locate Relevant Events

Use the incident's approximate time to narrow the investigation.
Review events around the incident rather than selecting an event solely because it has an Error or Critical level.

### Step 3 — Filter the Log

Use 'Filter Current Log' to narrow the displayed events by available criteria, such as:
- Event level
- Event source
- Event ID
- Time range

### Step 4 — Inspect Event Details

Open a relevant event and record:
- Date and time
- Source / Provider
- Event ID
- Level
- General message
- Relevant details

### Step 5 — Correlate With Other Evidence

Compare the event with the reported symptom, other nearby events, Reliability Monitor, service state, driver information, or recent system changes as appropriate.

## 5. Event Correlation and Timelines

An individual event provides only part of the available evidence.
A timeline can help establish the order in which events occurred.
Observation: What the log actually records.
Correlation: Whether events occur near the same time or share relevant context.
Hypothesis: A possible explanation for the observations.
Conclusion: What the combined evidence supports.

*Events occurring close together in time are not necessarily causally related.

## 6. Practical Observations

During Windows troubleshooting practice, the following events were examined:
| Event | Investigation Context |
|---|---|
| DCOM Event ID 10016 | Examined as an example of a recorded Windows component event |
| Kernel-Power Event ID 41 | Examined in the context of an unexpected restart |
| BugCheck Event ID 1001 | Examined in the context of a reported system crash |
| BugCheck code `0x116` | Examined as crash-related evidence |

These observations demonstrate the use of Event Viewer during troubleshooting. They do not independently establish the root cause of a system failure.

### Example: Kernel-Power Event ID 41

Kernel-Power Event ID 41 indicates that Windows detected that the previous system shutdown was not clean.

It does not, by itself, prove that the power supply, motherboard, or another particular component failed.

Further investigation may include:
- Checking for BugCheck events
- Reviewing the timeline around the restart
- Examining Reliability Monitor
- Reviewing relevant driver and hardware information
- Identifying evidence that is missing or inconclusive

### Example: BugCheck Event ID 1001

A BugCheck event may record information about a Windows system crash.
The recorded stop code and associated details can guide further investigation.

The code should be interpreted together with the crash context and other available evidence, rather than treated as automatic proof that a particular component is defective.

## 7. Limitations and Key Takeaways

- Event ID must be interpreted together with its source and message.
- Event severity alone does not establish incident severity or root cause.
- The absence of a relevant event does not prove that no problem occurred.
- Events may be missing, overwritten, delayed, or recorded in a different log.
- An event recorded near an incident may be unrelated.
- Kernel-Power Event ID 41 does not automatically indicate a power supply failure.
- BugCheck information is evidence for further investigation, not necessarily a complete diagnosis.
- Record observations separately from hypotheses and confirmed conclusions.

The objective is to use Event Viewer as one source of evidence within a structured troubleshooting process.
